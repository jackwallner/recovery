# Recharge target-user release audit

Audit ID: lsa817
Audit date: 2026-08-17
Product surface: iPhone app, Apple Watch app, iOS widget, Watch complications
Audience: product, design, engineering, release, and App Review owners

## Verdict

Do not release the current working tree.

The app has a coherent core idea, a strong countdown hero, a bounded model, and a thoughtful onboarding action layout. The current build is not ready for real users because the audit found defects that can make the displayed recovery time disagree with the persisted state, make stale Health data look current, obscure Settings content, mislead users with no history, and leave purchase pricing incomplete in the first paywall view.

The most important release blockers are:

1. The new cumulative recovery behavior is not persisted in SwiftData and does not have a model-version bump.
2. A failed Health read preserves and republishes a cached countdown without carrying a stale-data state to the Watch or widgets.
3. The floating tab bar visibly covers Settings content and can also cover Today and History content.
4. The current Release build is only a development-signed compile check. It contains the RevenueCat placeholder key and has get-task-allow enabled.
5. Watch and widget sync-state handling does not reliably distinguish never synced, successfully synced with no workout, stale, and out-of-order data.

These are user trust issues, not polish issues. A green model suite does not clear them.

## Severity rubric

- P0, release blocker: can make a user act on false data, lose trust in a paid or health-related decision, or encounter a primary surface that is materially broken.
- P1, must fix before broad release: affects a major target persona, important conversion or accessibility path, or a core device surface.
- P2, should fix before or immediately after release: meaningful quality, localization, or edge-case risk that does not invalidate the primary flow for most users.

## P0 release blockers

### P0-01. Cumulative recovery is calculated but not persisted

Affected users: anyone with two qualifying sessions while the first countdown is still active, especially frequent trainers, Garmin switchers, and users who close and reopen the app.

Evidence:

- The current model version remains 7 in [RecoveryModels.swift](Shared/Models/RecoveryModels.swift#L33).
- RecoveryEstimate in [RecoveryModels.swift](Shared/Models/RecoveryModels.swift#L469) now has carriedHours, totalHours, and isStacked.
- [RecoveryCalculator.swift](Shared/Utilities/RecoveryCalculator.swift#L100) computes the carried amount and uses it to set readyAt.
- [RecoveryEngine.swift](Shared/Services/RecoveryEngine.swift#L343) and [RecoveryEngine.swift](Shared/Services/RecoveryEngine.swift#L416) pass carried recovery into both scoring passes.
- RecoveryStateRecord in [RecoveryRecords.swift](Shared/Models/RecoveryRecords.swift#L100) has no persisted carriedHours field.
- RecoveryStateRecord.init(estimate:), estimate, and update(from:) at [RecoveryRecords.swift](Shared/Models/RecoveryRecords.swift#L125) do not write or restore the carried amount.
- The engine freezes records whose model version matches the current version at [RecoveryEngine.swift](Shared/Services/RecoveryEngine.swift#L464). Since stacking was added without changing version 7, existing version-7 records can remain frozen under pre-stacking semantics.
- The App Group snapshot uses estimate.totalHours at [RecoverySnapshot.swift](Shared/Models/RecoverySnapshot.swift#L66), but a rehydrated SwiftData estimate has a zero carried amount.

User impact:

On the first calculation in a process, a same-day second session can appear to extend the countdown. After persistence or a later refresh, that session can be rehydrated without the carried amount. The phone, history, Watch, widget, and conversion surfaces can then disagree about the total window or silently fall back to the session-only value. A user cannot reason about a countdown that changes merely because the app was relaunched.

Required fix:

- Bump the model version for the stacking behavior.
- Add an optional or migrated carriedHours property to RecoveryStateRecord.
- Persist and restore it in the initializer and update path.
- Decide explicitly whether each surface is showing session cost or total countdown. Use the same semantic for Today, History, the App Group snapshot, Watch, widgets, Rest Pattern, and personalized conversion preview.
- Add a migration test for old records and a persistence test that scores, saves, recreates, and reloads a same-day double.
- Add a test that a version bump thaws an old record and recomputes its current stacking semantics.

Release acceptance:

- After a cold launch, the second session still shows the same readyAt and total hours as before termination.
- The History detail, Today hero, Watch app, widget, and complication all agree.
- A legacy record without stacking data decodes as a truthful non-stacked estimate.
- A model version change cannot leave a stale pre-stacking record frozen.

### P0-02. Failed Health reads can leave a current-looking countdown on remote surfaces

Affected users: users who revoke Health access, go offline, have a transient HealthKit query failure, use a Watch or widget as their primary glance surface, or finish a workout while HealthKit is unavailable.

Evidence:

- fetchWorkouts() returns nil on query failure in [HealthKitService.swift](Shared/Services/HealthKitService.swift#L178).
- The engine intentionally preserves cached workouts when the read fails in [RecoveryEngine.swift](Shared/Services/RecoveryEngine.swift#L144).
- refresh() still imports context, rescoring, and publishes after the failed import path in [RecoveryEngine.swift](Shared/Services/RecoveryEngine.swift#L81).
- RecoverySnapshot in [RecoverySnapshot.swift](Shared/Models/RecoverySnapshot.swift#L15) stores calculatedAt, but not Health read state, last successful Health read, context freshness, or whether the displayed estimate used cached data.
- Today shows an error or freshness line near the bottom of the scroll content in [TodayView.swift](Recharge/Views/TodayView.swift#L472). A user looking at the hero may not see it.
- The Watch and widget read the same snapshot but have no equivalent stale-health state. The widget renders a countdown or Ready from the snapshot in [RechargeWidget.swift](RechargeWidget/RechargeWidget.swift#L45).

User impact:

Preserving cached history is the right data-retention choice, but the UI presents the preserved estimate as if it had just been confirmed. A user can finish a new workout, fail to import it, and continue to see an older countdown. A subscriber can see old sleep, HRV, or resting-heart-rate adjustments with no visible indication that the body signals are stale.

Required fix:

- Add explicit snapshot fields for Health read state, last successful workout import, last successful context import, and stale reason.
- Make stale status part of the display state on iPhone, Watch, widgets, and complications.
- Do not label cached estimates as current after a failed read.
- Keep the cached number available as historical context, but say that the latest Health data could not be read.
- Add a retry action close to the hero, not only at the bottom of Today.

Release acceptance:

- Failed import after a successful import displays a stale state on every surface.
- A successful empty import is distinguishable from a failed or denied read.
- A context failure does not silently look like a current personalized estimate.
- The Watch and widget never show an unqualified current countdown when the phone has marked the data stale.

### P0-03. The floating tab bar covers Settings and lower content

Affected users: all users, with a disproportionate impact on anyone changing Health, model, notification, or profile settings.

Evidence:

- [RootView.swift](Recharge/Views/RootView.swift#L48) places a capsule tab bar in a bottom ZStack overlay.
- [TodayView.swift](Recharge/Views/TodayView.swift#L90) adds a manual 72-point bottom padding.
- [HistoryView.swift](Recharge/Views/HistoryView.swift#L171) adds a manual 96-point bottom padding.
- [SettingsView.swift](Recharge/Views/SettingsView.swift#L22) uses a Form without equivalent clearance.
- The [settings screenshot](/tmp/recharge-audit-817/settings.png) visibly shows the tab capsule over the Recovery time section and its explanatory content.
- The [recovering screenshot](/tmp/recharge-audit-817/recovering.png) and [ready screenshot](/tmp/recharge-audit-817/ready.png) show the lower Why content entering the tab-bar region.
- The [history screenshot](/tmp/recharge-audit-817/history.png) shows the bottom bar over a day section and row.

User impact:

Settings content is not merely behind a decorative layer. The overlay can hide text, make a row appear cut off, and intercept the visual focus at the exact point where a user needs to understand or change the model. The manual clearances are also not coupled to the actual tab-bar height, so they are fragile under Dynamic Type, device size, orientation, and future copy changes.

Required fix:

- Apply one shared measured bottom inset at the shell level with safeAreaInset, or provide an equivalent inset to every tab.
- Remove screen-specific magic numbers.
- Add a UI test that scrolls the last row of Settings into view and checks its frame is above the tab bar.
- Test Today, History, and Settings at normal, large, and accessibility text sizes.

Release acceptance:

- Every scrollable surface can place its last interactive row fully above the tab bar.
- The tab bar never covers text, buttons, section headers, or disclaimers.
- The fix works on short screens and landscape if landscape remains supported.

### P0-04. The current Release build is not a shippable production artifact

Affected users: all production users if the wrong archive path or an incomplete release script is used.

Evidence:

- The current generic Release build compiled successfully, including the Watch and widget targets.
- Its signed entitlements contain get-task-allow=true, which is development signing, not App Store distribution signing.
- The compiled Release binary still contains appl_RECHARGE_PLACEHOLDER.
- The source placeholder is defined in [StoreService.swift](Shared/Services/StoreService.swift#L20).
- Production key substitution depends on [scripts/testflight.sh](scripts/testflight.sh#L17), which edits source temporarily, restores it on exit, and has no post-archive assertion that the placeholder is absent.
- The repository contains a previously uploaded build 20 archive, but its provenance relative to the current dirty source is not a release proof. The current source was not archived and exported through the production distribution path during this audit.

User impact:

The app may build and launch while the paywall cannot configure RevenueCat on a real device. A manual archive, alternate CI path, interrupted substitution, or wrong build script can produce a binary that is technically valid but monetization-inoperable.

Required fix:

- Make the release pipeline fail if the placeholder occurs in any Release product.
- Archive and export the exact current commit using App Store distribution signing.
- Inspect the archived iPhone app, Watch app, widget, entitlements, privacy manifests, and embedded binaries.
- Verify product loading, purchase, restore, pending, cancellation, expiry, refund, and offline behavior with the production catalog or an approved StoreKit test plan.
- Treat the generic Release build result as compile evidence only, not release evidence.

Release acceptance:

- No placeholder key occurs in the archived binary.
- The final archive has no get-task-allow.
- The archive uses the intended distribution profiles and contains the intended HealthKit and App Group entitlements.
- A clean install can load offerings and restore a purchase.

## P1 core product and device findings

### P1-01. First launch can say “No workout yet” while import is still running

Affected users: first-time users, users with a large Health history, reinstalling users, and people with slow Health queries.

History has an explicit importing state in [HistoryView.swift](Recharge/Views/HistoryView.swift#L63). Today derives its hero phase from the current estimate list, and the empty list renders “No workout yet” at [TodayView.swift](Recharge/Views/TodayView.swift#L167). The app starts the refresh from [App.swift](Recharge/App.swift#L33), while the Health failure and freshness messages are lower in the page.

User impact:

The first screen the user sees can imply that Apple Health has no workout history before the first query has finished. That is especially damaging after the user just granted access. It also makes a slow but successful import look like missing data.

Recommendation:

- Add a first-import state to Today.
- Use “Reading Apple Health…” or “Setting up your countdown…” in the hero while the first read is pending.
- Use an explicit “No qualifying workouts found” state only after a successful read with no qualifying result.
- Put retry and Health settings actions near the hero when the first read fails.

### P1-02. Health permission denial is not represented honestly enough

Affected users: privacy-sensitive users, users who allow workouts but deny heart rate or context, and users who have no Health history.

HealthKit does not reveal individual read grants. [HealthKitService.swift](Shared/Services/HealthKitService.swift#L104) treats a request without a thrown error as sufficient to set the authorized state, while query errors and denied reads can produce empty results. Settings acknowledges the ambiguity, but the user-facing path can still read as connected with no workouts.

Recommendation:

- Do not claim “Connected” solely because authorization request status returned without error.
- Use distinct copy for “no readable data,” “no qualifying history,” “query failed,” and “HealthKit unavailable.”
- Keep the access card visible until at least one qualifying read has succeeded.
- Provide a direct route to Health settings and explain that Apple does not disclose per-type read permission.

Required test matrix:

- Allow all requested reads.
- Deny workout reads.
- Allow workouts but deny heart rate.
- Allow workouts but deny sleep, HRV, and resting heart rate.
- Revoke access after a successful import.
- HealthKit unavailable.
- Successful access with no qualifying workouts.

### P1-03. No-history onboarding shows an empty Health section and can show unlabeled examples

Affected users: people who have never recorded a qualifying workout, people returning from inactivity, non-athletes, and users evaluating the trial before their first workout.

The onboarding page title says “Here’s what Health already knew,” but [OnboardingView.swift](Recharge/Views/OnboardingView.swift#L395) can render no Health rows. The footer can still say that this is everything Recharge needs. The model creates canonical example Rest Pattern rows in [RestPattern.swift](Shared/Utilities/RestPattern.swift#L222), while the compact onboarding card omits its example footnote in [RestPatternCard.swift](Recharge/Views/Components/RestPatternCard.swift#L37).

User impact:

A person with no history can see a card titled “Your rest pattern” and values in the “Yours” column before the app has observed any rest pattern. Blurring a number does not communicate that it is an example. This is a serious trust problem in the exact conversion surface where the user is deciding whether to subscribe.

Recommendation:

- Show an explicit empty Health state, such as “No qualifying workouts yet. Recharge starts learning when Apple Health has a hard session.”
- Label every example row, including the blurred column, as an example.
- Do not call it “Your rest pattern” until the required measurements exist.
- Let the user reach the free Today state before asking them to evaluate the paid comparison, or make the free path materially more prominent.

### P1-04. The strength effort explanation does not match the load algorithm

Affected users: strength lifters, users with incomplete heart-rate coverage, and anyone who answers the effort prompt honestly.

Today says “Heart rate was unreliable, so your rating decides the estimate” at [TodayView.swift](Recharge/Views/TodayView.swift#L337). The strength load path takes the maximum across heart rate, effort, energy, and duration in [SessionLoadCalculator.swift](Shared/Utilities/SessionLoadCalculator.swift#L65).

User impact:

The copy promises that the rating decides the number, but a different source can still win. A user can answer the question and see little or no change, or see a number governed by duration or energy without knowing why. This undermines the explicit trust contract created by the prompt.

Recommendation:

- Say that the rating helps fill in an incomplete estimate.
- Explain which load source won and whether the effort answer changed the result.
- Show a short strength-specific explanation in History detail.
- Test clean HR, partial HR, energy only, effort only, and all-source strength sessions through the actual UI.

### P1-05. Free-tier copy contradicts the actual training-level scaling

Affected users: free users, Garmin switchers, serious athletes, and users whose profile changes after import.

The Store copy says the standard estimate is “the same table for everyone” in [description.txt](fastlane/metadata/en-US/description.txt#L27). The code and current product copy use the training level a user states or the engine derives, including weekly volume and experience, through [AthleteProfile.swift](Shared/Utilities/AthleteProfile.swift#L219) and [RecoveryEngine.swift](Shared/Services/RecoveryEngine.swift#L120).

User impact:

Two free users can receive different estimates. A single free user can also receive different estimates after enough Health history derives a new training-volume bucket. The product promise currently tells users that this cannot happen.

Recommendation:

Use wording such as:

“The standard method is shared, then scaled to the training level you state or Recharge observes.”

The paywall can still distinguish the measured personal baseline from the shared standard method. The distinction should be methodology, not a false claim of identical output.

### P1-06. Partial sensor quality is hidden at the point where the user acts

Affected users: users with partial permissions, older or third-party workout sources, strength users, endurance athletes, and subscribers.

The estimate can be based on heart rate, effort, energy, or duration. Confidence is shown in the hero, while the load source and heart-rate coverage are mainly exposed inside History detail at [HistoryView.swift](Recharge/Views/HistoryView.swift#L434).

User impact:

A user sees a long countdown but cannot immediately tell whether it came from a strong heart-rate trace or a low-confidence duration fallback. “High confidence” can be read as physiological certainty even though it describes the model input.

Recommendation:

- Put “Using heart rate,” “Using effort,” “Using energy estimate,” or “Using duration fallback” near the current estimate.
- Show heart-rate coverage when relevant.
- Explain that confidence describes signal quality, not medical certainty.
- Show when a context signal was missing or stale.

### P1-07. Context query failures silently become missing context

Affected users: Recharge+ subscribers, users with partial permissions, and users whose Apple Health context data is delayed.

RHR, HRV, and sleep queries return empty collections on errors in [HealthKitService.swift](Shared/Services/HealthKitService.swift#L296). importContext() then returns without recording a failure in [RecoveryEngine.swift](Shared/Services/RecoveryEngine.swift#L215). Workout background delivery is enabled, but context freshness is not separately represented.

User impact:

A paid user can lose sleep, HRV, or RHR adjustment without an explanation. Existing context records may remain visible to the model while the current read has failed, creating an unmarked mixture of old and new data.

Recommendation:

- Track success and freshness independently for workouts and each context signal.
- Show which signals contributed to the active estimate.
- Enable background delivery where supported, or state when a foreground refresh is required.
- Add failure and partial-data tests.

### P1-08. Watch and widget sync states are incomplete

Affected users: users who add a complication before opening the Watch app, users with no workout history, users who reinstall, and users who use an iOS widget before the first phone publish.

The Watch complication derives its sync state from snapshot.hasSession in [WatchComplication.swift](RechargeWatchWidget/WatchComplication.swift#L73). An empty snapshot after a successful delivery still has no session, so it can display the never-synced “Open Recharge to set up” state. The iOS widget similarly maps an empty snapshot to “No workout” in [RechargeWidget.swift](RechargeWidget/RechargeWidget.swift#L76).

The Watch app itself has a better lastSnapshotReceived concept in [PhoneWatchSession.swift](Shared/Services/PhoneWatchSession.swift#L67), but the complication extension cannot use that observable object. The shared snapshot needs a durable received-state marker or equivalent metadata.

Recommendation:

- Carry a distinct sync state in the shared snapshot or in the extension-readable App Group.
- Cover never synced, synced with no workout, current workout, stale workout, and cleared data.
- Use “Open Recharge to finish setup” only when no snapshot has ever arrived.
- Use “No recent qualifying workout” after a valid empty snapshot.

### P1-09. WatchConnectivity sends ordering metadata but does not enforce it

Affected users: users with queued Watch transfers, intermittent Bluetooth, or a Watch that reconnects after being offline.

The phone adds sentAt to its payload in [PhoneWatchSession.swift](Shared/Services/PhoneWatchSession.swift#L330). The Watch narrows the payload and applies it in [PhoneWatchSession.swift](Shared/Services/PhoneWatchSession.swift#L274), but does not compare sentAt with the last accepted payload. The receiver stores the local receive time rather than the source timestamp.

User impact:

An older queued transferUserInfo payload can overwrite a newer application context and move the Watch backwards to an older countdown. A countdown that regresses after a reconnect will look broken and can change the user’s behavior.

Recommendation:

- Persist the last accepted source timestamp.
- Reject payloads older than the accepted timestamp.
- Treat malformed or missing timestamps as a separately logged degraded path.
- Add an out-of-order delivery test using application context followed by an older user-info payload.

### P1-10. Watch effort state is visible, but the first viewport clips the supporting detail

Affected users: lifters who open the Watch immediately after a session, especially on smaller watches or with larger text.

The [Watch effort screenshot](/tmp/recharge-audit-817/watchEffort.png) shows the Rate effort action clearly, but the Ready tomorrow detail is cut at the bottom of the first viewport. The screen uses a ScrollView in [WatchTodayView.swift](RechargeWatch/Views/WatchTodayView.swift#L29), so the content may be reachable by scrolling, but the primary context is not visible together with the action.

Recommendation:

- Keep the effort prompt, session label, and a short sync consequence in the first viewport.
- Make the button and its supporting context fit on the smallest supported Watch.
- Test with larger text and with a pending effort state after a real phone import.
- Add a Watch UI test or screenshot test that verifies the prompt and session identity are simultaneously visible.

### P1-11. Paywall first frame does not show a complete purchase decision

Affected users: trial users, first-time buyers, older users, low-vision users, and App Review.

The CTA is pinned with safeAreaInset in [PaywallView.swift](Recharge/Views/PaywallView.swift#L69), while the plan cards live in the scroll content at [PaywallView.swift](Recharge/Views/PaywallView.swift#L158). In the [paywall screenshot](/tmp/recharge-audit-817/paywall.png), the selected Yearly card begins behind the pinned CTA. The visible first frame does not show the selected plan’s full billed amount and trial context together with the purchase action. The disclosure below the CTA is also fixed at 11 points and tertiary color at [PaywallView.swift](Recharge/Views/PaywallView.swift#L275).

The UI test checks that the plan labels and CTA exist and that scrolling reaches legal links. It does not check that the selected plan’s billed amount is visible on first presentation.

Recommendation:

- Keep the pinned CTA, but add a selected-plan summary above it, or add enough bottom content inset to keep the entire selected card above the CTA.
- Make the billed amount and trial renewal terms readable without scrolling.
- Use a scalable text style for the disclosure and verify it at the largest supported text sizes.
- Verify each yearly, monthly, and lifetime selection, not only the default yearly plan.

Release acceptance:

- The selected plan, amount billed, trial or no-trial status, renewal cadence, and CTA are visible together.
- The disclosure remains readable at accessibility sizes.
- Restore, Terms, Privacy, retry, pending, and purchase errors remain reachable.

### P1-12. Purchase state changes can recalculate the active countdown without an impact warning

Affected users: trial users, restoring subscribers, users whose subscription expires, and users comparing free and paid numbers.

Entitlement changes call the engine rescore path from [StoreService.swift](Shared/Services/StoreService.swift#L117) and [RecoveryEngine.swift](Shared/Services/RecoveryEngine.swift#L713). The paywall explains paid features but does not prominently say that the active countdown, Watch value, and widget value can change immediately.

Recommendation:

- Add a short notice before purchase or restore: “Recharge+ may recalculate your current countdown using your history and body signals.”
- Show the standard and personalized values when available.
- Explain what happens when a trial ends or a subscription is canceled.
- Add UI and model tests for purchase, restore, expiry, and loss of entitlement while a countdown is active.

## P1 accessibility, comprehension, and compliance findings

### P1-13. Dynamic Type is inconsistent and capped in legally important surfaces

Affected users: older users, low-vision users, users with AX text sizes, and users evaluating a paid trial.

Evidence:

- The onboarding CTA caps its title at accessibility2 in [OnboardingActions.swift](Recharge/Views/Components/OnboardingActions.swift#L99).
- Onboarding legal links cap at large in [OnboardingActions.swift](Recharge/Views/Components/OnboardingActions.swift#L140).
- The paywall uses fixed 9, 10, and 11 point styles in [PaywallView.swift](Recharge/Views/PaywallView.swift#L207) and [PaywallView.swift](Recharge/Views/PaywallView.swift#L339).
- Watch countdown and detail copy use fixed sizes in [WatchTodayView.swift](RechargeWatch/Views/WatchTodayView.swift#L111).
- The main Today countdown uses a fixed theme size, one line, and an aggressive minimum scale factor in [TodayView.swift](Recharge/Views/TodayView.swift#L193).
- Tab labels use a fixed small size in [RootView.swift](Recharge/Views/RootView.swift#L54).
- The only targeted large-text UI test covers the onboarding trial offer.

The only large-text UI test does not prove the full flow at AX sizes. The test suite proves CTA reachability on one offer state, not legal copy, Today, History, Settings, the full paywall, Watch, or widgets.

Recommendation:

- Prefer scalable system text styles.
- Keep the CTA stable with layout constraints, not by shrinking legal text.
- Add a matrix for all major screens at AX3 through AX5.
- Test long localized strings even if launch is currently English-only.

### P1-14. Important controls may not meet a reliable touch target

Affected users: users with motor impairments, users wearing gloves, and one-handed users.

Several controls use compact text and padding without an explicit 44-point hit area:

- Today Health and Pro actions in [TodayView.swift](Recharge/Views/TodayView.swift#L367).
- The onboarding Restore, Terms, and Privacy row in [OnboardingActions.swift](Recharge/Views/Components/OnboardingActions.swift#L140).
- Paywall Restore, Terms, and Privacy in [PaywallView.swift](Recharge/Views/PaywallView.swift#L316).
- Small Watch and complication controls use fixed compact typography.

Recommendation:

- Give every interactive control a minimum 44-point frame or content shape.
- Add hit-rectangle assertions rather than only checking that an element exists.
- Check the floating tab buttons at the smallest supported screen.

### P1-15. Rest Pattern is visually dense and can look more personal than it is

Affected users: free users, no-history users, low-vision users, and anyone unfamiliar with the column semantics.

The card compresses four columns into one row in [RestPatternCard.swift](Recharge/Views/Components/RestPatternCard.swift#L72). Headings and values use one-line constraints and scale factors at [RestPatternCard.swift](Recharge/Views/Components/RestPatternCard.swift#L93). The combined VoiceOver label is a good control, but the visual layout still makes measured You, standard Similar, and paid Yours look like equivalent facts.

The [recovering screenshot](/tmp/recharge-audit-817/recovering.png) shows the card is readable at default size, but it occupies a large portion of the first screen and pushes the explanatory Why content below the tab overlay.

Recommendation:

- Use a stacked row layout at larger text sizes or narrow widths.
- Use stronger visual labels for measured, standard, and personalized values.
- Keep the combined accessibility label and include whether a value is measured, an example, or an estimate.
- Do not show “Your rest pattern” or blurred personal values as established personal facts before the required history exists.

### P1-16. Bare “Ready” wording on glance surfaces can be read as clearance

Affected users: Watch and widget users who do not open the iPhone app, especially older users and Garmin switchers.

The iPhone includes non-medical disclaimers. Watch, widget, and complication strings use “Ready” and “Ready for another hard session” in [RechargeWidget.swift](RechargeWidget/RechargeWidget.swift#L76), [WatchTodayView.swift](RechargeWatch/Views/WatchTodayView.swift#L203), and [ComplicationCopy.swift](Shared/Utilities/ComplicationCopy.swift#L60).

The wording avoids stronger banned phrases such as “safe to train,” which is good. A glance-only user can still interpret bare Ready as a health clearance rather than a cardiovascular training estimate.

Recommendation:

- Use “Estimate ready” or “Cardio estimate ready” where space allows.
- Keep the qualifier in the Watch app and widget detail.
- Review every glance string as a product-level compliance set, not only through banned-word tests.

### P1-17. Age and biological-sex inputs are not transparent enough

Affected users: older users, women, users without a recorded biological sex, and users who do not want a binary formula chosen silently.

The app reads date of birth and biological sex in [HealthKitService.swift](Shared/Services/HealthKitService.swift#L134), and uses them in the heart-rate range. The onboarding explains age but does not clearly explain that sex selects the max-heart-rate formula. The settings About You section does not provide a clear inspection or override path. Broad age answers are converted to an approximate age.

Recommendation:

- Explain in plain language which inputs affect heart-rate normalization.
- Provide an optional visible max-heart-rate method or tested max-heart-rate override.
- State how broad age bands are converted.
- Explain the fallback when the Health characteristic is missing or declined.
- Review whether biological sex is the right product input and how it should be presented to users who do not identify with the available choices.

### P1-18. Confidence can imply more evidence than the baseline has

Affected users: serious athletes, subscribers, and users who act on the High confidence label.

The baseline confidence boundary uses a session count in [RecoveryBaseline.swift](Shared/Utilities/RecoveryBaseline.swift#L74), while the actual shrinkage weight is based on training days in [RecoveryBaseline.swift](Shared/Utilities/RecoveryBaseline.swift#L131). A high-frequency athlete can reach the session threshold in a few days while the baseline is still heavily shrunk toward the standard reference.

Recommendation:

- Base Building baseline on evidence that matches the actual shrinkage rule, or explain both session count and training-day evidence.
- Define Low, Medium, High, and Building baseline in user-facing copy.
- State that confidence describes input and model evidence, not fitness to train or medical certainty.

### P1-19. ReviewPromptSheet is fixed to a medium detent and has no scroll path

Affected users: users with larger text, users entering feedback, and users with a small display.

[ReviewPromptSheet.swift](Recharge/Views/ReviewPromptSheet.swift#L34) uses a fixed medium detent and no scroll container. The feedback editor is fixed at 110 points at [ReviewPromptSheet.swift](Recharge/Views/ReviewPromptSheet.swift#L120).

Recommendation:

- Add a larger detent or a scrollable sheet.
- Test every review stage at accessibility sizes.
- Ensure the feedback error and Send action remain visible when the keyboard appears.

### P1-20. Privacy copy contradicts RevenueCat handling

Affected users: privacy-sensitive users and subscribers.

The App Store description says there is “no server” at [description.txt](fastlane/metadata/en-US/description.txt#L58). RevenueCat is configured in [StoreService.swift](Shared/Services/StoreService.swift#L20). The local Settings footer is more accurate and says purchase information is handled by Apple and RevenueCat at [SettingsView.swift](Recharge/Views/SettingsView.swift#L543).

Recommendation:

Replace the absolute claim with wording such as:

“Your Health data, answers, and estimates stay on your devices. Purchases and entitlement status are handled by Apple and RevenueCat.”

Reconcile the App Store description, privacy policy, privacy nutrition labels, app privacy manifest, RevenueCat SDK disclosures, and all localized metadata. [PrivacyInfo.xcprivacy](Shared/PrivacyInfo.xcprivacy#L9) should be checked against the archived merged manifests and the actual SDK behavior.

### P1-21. The Watch HealthKit purpose strings do not match the architecture

Affected users: Watch users, App Review, and anyone who sees a permission explanation.

The Watch intentionally does not compute the model or read HealthKit. It receives the phone-owned snapshot. [RechargeWatch/Info.plist](RechargeWatch/Info.plist#L25) says the Watch reads workouts and heart data from Apple Health.

Recommendation:

- Verify whether the string appears in any real Watch permission sheet or only exists for upload validation.
- If it can appear, say that the iPhone reads Health and the Watch receives the estimate.
- Inspect the final archive rather than relying on source comments about why the strings remain.

## P1 persona walkthroughs

### Persona A: first-time user with no Health history

Expected need: understand what the app does, grant access, and know what will happen after the first workout.

Observed risk:

- Health readout can be empty under a heading that implies data was found.
- The free and paid paths can show example Rest Pattern values before any qualifying history exists.
- Today can briefly say “No workout yet” while import is still running.
- An empty widget can say “No workout” even when it has never received a snapshot.
- The user is asked to consider Recharge+ before seeing a real result.

Must pass:

- Clear no-history state.
- Clearly labeled examples.
- No false connected state.
- Visible free path.
- Widget says setup or no qualifying workout according to actual sync state.

### Persona B: Garmin switcher who trains twice in a day

Expected need: cumulative recovery behavior, stable history, and parity that is framed honestly.

Observed risk:

- Stacking is not persisted.
- Model version 7 can freeze old records under pre-stacking semantics.
- Conversion preview, Rest Pattern, and current countdown have different session-versus-total semantics.
- Garmin-style language can be read as methodology or value parity, although the strength path and maximum differ.

Must pass:

- Same-day double remains cumulative after relaunch.
- Phone, Watch, widget, and History agree.
- The Garmin comparison states what is analogous and what is different.

### Persona C: serious endurance athlete

Expected need: high-quality heart-rate provenance, correct max-HR normalization, and transparent context freshness.

Observed risk:

- Partial sensor quality is not shown in the hero.
- Failed or stale context queries can silently remove paid adjustments.
- Heart-rate coverage is estimated by sample count and does not deduplicate overlapping sources.
- High confidence can be interpreted more strongly than the evidence warrants.

Must pass:

- Show the load source and coverage.
- Show context freshness.
- Test duplicate, sparse, and third-party samples.
- Explain confidence as model input quality.

### Persona D: strength lifter

Expected need: a believable result despite intermittent optical heart rate, plus a usable effort prompt.

Observed risk:

- Prompt copy says the rating decides the estimate even though the algorithm takes a maximum across sources.
- Stacking persistence is especially important for frequent lifting.
- Watch effort state clips supporting detail in the first viewport.

Must pass:

- Explain the winning source.
- Effort answer changes the estimate when it should and does not claim to be the only source.
- Watch prompt, session identity, and sync consequence are visible together.

### Persona E: mixed-sport or HYROX user

Expected need: per-session classification because one week can contain strength-biased circuits and conditioning-biased sessions.

Observed risk:

- Ambiguous activity types share a global profile setting.
- Per-session correction is paid.
- Unknown future HealthKit activity codes can fall back silently.

Must pass:

- Show the applied profile before accepting a long countdown.
- Offer a per-session correction or clearly state the limitation.
- Add unknown-activity fixtures and a safe user-facing fallback.

### Persona F: free user comparing the product

Expected need: understand the free result and the paid difference without being misled.

Observed risk:

- Same table for everyone does not match training-level scaling.
- Similar and Yours are visually similar columns.
- Purchase can change the active countdown without a prominent warning.

Must pass:

- Explain standard method versus personalized input.
- Show a clear standard versus personalized comparison.
- Tell the user that entitlement can recalculate the active window.

### Persona G: older or low-vision user

Expected need: readable text, stable layout, and trustworthy purchase disclosure.

Observed risk:

- Settings is obscured by the tab bar.
- Paywall legal copy is small, tertiary, and low prominence in the screenshot.
- Legal links are capped at smaller Dynamic Type.
- The Rest Pattern table shrinks horizontally.
- Watch detail uses fixed sizes.

Must pass:

- No overlay obstruction.
- AX3 to AX5 layouts remain readable and scrollable.
- Pricing and renewal copy remain visible next to the CTA.
- VoiceOver announces the current estimate, source, stale state, and disclaimer.

### Persona H: Watch-first user

Expected need: reliable background delivery without opening the Watch app.

Observed risk:

- Complication state is inferred from whether a session exists, not whether a snapshot was received.
- Older queued payloads can be applied after newer ones.
- The Watch path has no physical-device verification in this audit.

Must pass:

- Fresh install, never-opened Watch app, phone publish, complication update.
- Empty synchronized state is not called never synced.
- Stale and out-of-order payloads are rejected or labeled.

### Persona I: privacy-sensitive user

Expected need: know what Health data stays local and what purchase infrastructure receives.

Observed risk:

- No server contradicts RevenueCat handling.
- Watch HealthKit purpose text does not match the phone-owned architecture.
- Biological-sex use is not transparent enough.

Must pass:

- Consistent privacy language across Settings, App Store, policy, manifest, and purchase SDK.
- Clear explanation of Health data flow and purchase data flow.
- Understandable optionality around max-HR inputs.

### Persona J: offline or revoked-permission user

Expected need: never mistake a cached estimate for a current Health-confirmed result.

Observed risk:

- Cached workouts are retained after a failed read.
- The iPhone places the failure low in Today.
- Watch and widgets lack a stale state.

Must pass:

- Current estimate is visibly marked stale.
- Last successful import time is visible.
- Retry and Health settings paths are easy to find.

## P2 findings and release hygiene

### P2-01. App Store screenshots do not match the current UI

The current Today screen includes Rest Pattern before Why, while the existing screenshot set inspected by the Luna layout worker does not. Current History collapses quiet sessions by default, while the older screenshot shows an expanded quiet row. Recapture all store assets from the current source, at both supported iPhone sizes, after the layout blockers are fixed.

### P2-02. English-only in-app UI needs a product decision

No strings or xcstrings resources were found in the app sources, while the repository contains multiple localized App Store metadata directories. Either localize the in-app experience, especially pricing and legal copy, or limit the supported storefront regions and claims deliberately.

### P2-03. Landscape is declared but not audited

[Recharge/Info.plist](Recharge/Info.plist#L35) declares portrait, landscape, and upside-down orientations. The UI tests run portrait only, and the screenshots are portrait only. Either remove unsupported orientations or test Today, History, Settings, onboarding, and paywall in each supported orientation.

### P2-04. Persistence failures are swallowed

Several SwiftData saves use try?, including import, context import, scoring, feedback, and setting paths. [DataService.swift](Shared/Services/DataService.swift#L15) deletes the store and recreates it if opening fails. This is a defensible last-resort recovery strategy, but it needs logging and a user-visible recovery state when the store is lost. A user should not silently lose cached history and assume the app has simply reset.

### P2-05. Heart-rate coverage can be inflated by duplicate sources

[HealthKitService.swift](Shared/Services/HealthKitService.swift#L247) assumes five seconds of coverage per sample and does not deduplicate overlapping samples. A workout imported from more than one source can therefore appear to have better coverage than it did. Add fixtures with overlapping and duplicate samples, and make the source policy explicit.

### P2-06. Weekly volume has no none or starting-again answer

The weekly-volume choices begin at one to two sessions in [AthleteProfile.swift](Shared/Utilities/AthleteProfile.swift#L100). A non-athlete or a person returning from illness or injury must choose an inaccurate answer or skip the question. Add None right now or I’m starting, and explain that Recharge only produces a countdown after a qualifying session.

### P2-07. Ambiguous activity classification is global

Functional training and HIIT can share one global ambiguous profile in [SettingsView.swift](Recharge/Views/SettingsView.swift#L330). A user who mixes conditioning circuits and strength circuits cannot represent both accurately without a per-session correction. Offer per-session classification or a one-time mapping per activity type, and treat unknown future activity codes as needing classification rather than silently choosing endurance.

### P2-08. Garmin positioning should be narrower

The product says “It is the answer a Garmin gives you” in onboarding and App Store copy. A non-affiliation disclaimer exists, but the phrase can imply methodology, values, or endorsement parity. Prefer Garmin-style recovery estimate, then state the material differences: Apple Health inputs, 72-hour maximum, phone-owned model, and custom strength and mixed-sport handling.

### P2-09. Watch and app HealthKit purpose copy should be reconciled

The phone reads Health. The Watch receives a snapshot. The Watch Info.plist says the Watch reads workouts and heart data. Confirm the final user-visible permission behavior and rewrite the purpose text if necessary.

### P2-10. Model version and source version should be visible in support diagnostics

History includes model version, which is useful. Add a support-readable data freshness timestamp, app build, snapshot source, and persisted stacking state. This will reduce ambiguity when a user reports that Today, History, and the Watch disagree.

## What is working and should be preserved

- The product proposition is easy to understand: a countdown after a qualifying workout and a Ready state when it expires.
- The phone-owned model architecture avoids a second, diverging Watch calculation.
- The pure model suite is unusually strong. It covers every HealthKit activity code, multiple personas, sensor availability, monotonicity, bounded output, strength behavior, Garmin anchor bands, high-volume histories, and stacking calculations.
- The standard and personalized paths are explicitly separated in the model.
- The onboarding action block has stable geometry and a clearly named free path.
- History has a valuable detail view with load source, heart-rate coverage, tier, confidence, and model version.
- The iPhone hero has a strong information hierarchy and a clear phase transition.
- The Watch recovering and Ready screens are compact and understandable at default size.
- The app includes non-medical disclaimers on iPhone surfaces and complication copy tests reject stronger claims such as safe to train.
- The paywall has loading, error, retry, restore, pending, and legal-link paths.
- The app preserves cached history rather than deleting it after a failed Health read. The missing piece is truthful stale-state presentation.

## Final release decision

Current decision: No-go.

The core countdown experience is promising and the test coverage catches many model regressions. The release should wait until the P0 state, freshness, layout, and production-artifact issues are fixed and the P1 persona paths are exercised on device. The strongest next verification is a clean distribution archive followed by a paired iPhone and Watch smoke test using a real HealthKit store and a real purchase state.

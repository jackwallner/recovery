## Decisions taken during the build

The build plan left four questions open. Three were answerable from the model
itself and were decided as proposed; the fourth is still Jack's.

1. **Ready-state threshold** — as proposed: the 25th percentile of the person's
   own sessions, floored at `RecoveryCalculator.absoluteCountdownFloor` (18 load
   units, about a 20-minute walk). `testShortWalkBelowTheFloorStartsNoCountdown…`
   pins the floor, `testQuietThresholdUsesTheUsersOwn25thPercentile…` the
   percentile.
2. **HYROX / CrossFit default** — as proposed: both ambiguous activity types
   default to `mixed`, with a Settings-level default and a per-session override
   in History. `WorkoutClassifierTests` covers all three paths.
3. **Free vs Pro on the complication** — confirmed as `positioning.md` had it.
   All four families are Free. The complication is the product for a 28-second
   session; putting it behind the paywall would remove the reason to keep the app.
4. **Marketing site at launch** — pages are written and ready in `docs/`, but
   GitHub Pages is not enabled and the repo has no remote. Still Jack's call.

## The fixture table

Printed from `FixtureTableTests/testPrintFixtureTable`, no context (free tier):

```
fixture                       profile    load     source         rel    category    window
30-min easy walk              easy       9.9      heartRate      0.16   Easy        — no countdown
45-min easy run               endurance  55.3     heartRate      0.91   Typical     11 to 15h
60-min threshold run          endurance  157.3    heartRate      2.60   Very hard   43 to 58h
90-min long run               endurance  157.7    heartRate      2.61   Very hard   43 to 58h
45-min ride                   endurance  67.9     heartRate      1.12   Typical     14 to 18h
60-min lift, no HR            strength   57.6     energy         0.58   Easy        — no countdown
60-min lift, RPE 8            strength   144.0    reportedEffort 1.44   Hard        22 to 30h
70-min HYROX                  mixed      189.0    reportedEffort 1.38   Hard        23 to 32h
50-min run (dupe A)           endurance  92.0     heartRate      1.52   Hard        21 to 28h
new user, 45-min run          endurance  55.3     heartRate      0.79   Typical     9 to 13h
```

**Two rows to look at before this ships.**

- A 60-minute threshold run produces **43 to 58h**. That is high against Garmin,
  which would put a hard hour nearer 24-36h. The cause is structural and known:
  relative load is measured against the **median** of the fixture history, and a
  median dominated by easy sessions makes a genuinely hard session read as 2.6x
  typical. `README.md` flags exactly this as open tuning question 1, and the fix
  (percentile rank rather than a ratio to the median) was deliberately deferred
  until there is real user data. Worth confirming the numbers feel right before
  launch rather than after.
- **A 60-minute lift with no heart rate and no effort answer produces no
  countdown at all** (relative load 0.58, below the quiet threshold). This is the
  model being honest — it has no signal — and it is exactly the case the RPE
  prompt exists for: the same session at RPE 8 produces 22 to 30h. But a user who
  ignores the prompt sees a hard session score as nothing, which will read as a
  bug. Consider whether an unanswered strength session should carry the profile's
  assumed effort rather than falling through to energy.

## Deviations from the plan

- **An iOS widget was added** (`RechargeWidget`, small + medium). The plan only
  listed Watch complications, but the timeline work was already done and the
  extension target was already in `project.yml`.
- **`scripts/xcgen.sh` replaces bare `xcodegen generate`.** XcodeGen writes
  `storeKitConfiguration` into a scheme's Launch action only, and `xcodebuild
  test` runs the Test action. See the paywall note below.
- **StoreKit product IDs are bundle-prefixed** (`com.jackwallner.recharge.yearly`).
  Bare identifiers like `yearly` are silently not vended by StoreKit.

## Unverified

Listed because "built" and "verified" are not the same thing.

1. **The paywall plan cards.** Everything else on the paywall renders and is
   asserted — hero, all six feature rows, the neutral CTA, Restore, Terms,
   Privacy — and there is a captured screenshot of it. The three plan cards are
   not. StoreKit Testing does not activate under `xcodebuild test` on this
   toolchain: the `.storekit` file is referenced from `RechargeUITests.xctestplan`
   *and* patched into the scheme's TestAction, IDs are bundle-prefixed, and
   `Product.products(for:)` still returns empty without throwing.
   `testPaywallRendersRealProductsUnderStoreKitTesting` skips rather than fails,
   so the gap is visible instead of red. **Run the `Recharge` scheme from Xcode
   once and look at it before shipping.**
2. **The Watch → phone RPE path end to end.** The code is there and both sides
   compile and run, but a paired simulator does not exercise WatchConnectivity
   the way hardware does. Needs a real iPhone and Watch.
3. **Background delivery.** `HKObserverQuery` + `enableBackgroundDelivery` cannot
   be exercised on simulator. Needs a real workout on a real device.
4. **Anything requiring App Store Connect.** No app record exists, so no IAP
   configuration, no intro offers, no PPP pricing, no TestFlight build. The
   scripts to do all of it are in `scripts/` and are the same ones the rest of
   the fleet uses.

B3

If the SwiftData store has to be quarantined, the saved HealthKit anchor keeps workouts from ever re-importing

mediumplausibledata
Impact

After a store failure the countdown, history, effort answers and intensity overrides vanish and the app does not recover on its own. Nothing tells the user why.

How it happens

  4. The anchored query returns only changes after that anchor, so the new store stays empty. Today shows No recent workout and History shows nothing until the user finds Settings > Delete local health data (the only code path that resets the anchor).
  5. In the in-memory fallback the anchor is committed after each import, so a relaunch loses the data in the same way.

B6

A hard session's Ready moment is never counted if an easy session ended inside its countdown

lowconfirmedstate
Impact

People who do anything easy after a hard session (common) never get that countdown counted as a Ready moment. The review ask that is meant to fire right after the win is lost for those sessions, and the user only gets the slower engaged-use ask (6 launches and 7 days). The readiness question and the Ready alert are not affected: they use other paths.

How it happens
  1. Finish a hard run that starts a multi-day countdown (a Recharge+ or free account, setup already complete).
  2. A few hours later finish an easy session that starts no countdown (a walk, easy yoga). Its countdown is empty, so the run's countdown keeps running.
  3. Wait for the run's countdown to run out, with the phone open or closed.
  4. RecoveryEngine.publish() and handleClockTick() ask RecoveryResolver.readyMoment for the Ready moment. It resolves current(), which is the newest session by end time (the walk), sees it has no countdown, and returns nil.
  5. ReviewPromptTracker.recordReadyMoment is never called for the run, so readyMomentCount does not grow and the Ready-moment review ask never arms.
Where
Shared/Utilities/RecoveryResolver.swift:123Shared/Utilities/RecoveryResolver.swift:24Shared/Services/RecoveryEngine.swift:1011Shared/Services/RecoveryEngine.swift:1246
Suggested fix

Resolve the Ready moment from the countdown-producing estimates only, for example the one with the latest readyAt that is at or before now, instead of current().

Evidence
guard let eligibleFrom,
      let estimate = current(in: estimates, now: now),
      estimate.producesCountdown,
      estimate.readyAt <= now,
      estimate.readyAt >= eligibleFrom
else { return nil }
return estimate

current() returns the active countdown while one is running, otherwise the newest session by sessionEnd, whether or not it produced a countdown. The walk is newest and has producesCountdown false, so the guard fails and the run is never considered. awaitingFeedback filters the whole list instead of calling current(), which is why the readiness question still works and this does not.

Not proven: Whether the product wants the run's expiry to count when a later easy session is what Today then names. The code comment says a countdown the user had should count.

Checked and ruled out (36)
  • Phone clock times and weekday names use static formatters that never refresh after a time zone or 12/24 hour change: A date formatter with no fixed time zone follows the system zone, and iOS resets that when the zone changes; no stale time was shown.
  • Paying customer shown as free when launching offline: RevenueCat hands cached CustomerInfo to the delegate when it is assigned (StoreService.swift:591, SDK behavior recalled, not verified here), and scoring falls back to KnownEntitlement. Screens gate on isPro only.
  • Purchase succeeds but access is not granted: purchase() calls apply(customerInfo:) before returning, isPro flips, and its didSet calls entitlementDidChange so the engine rescores and republishes.
  • Offerings load failure strands the paywall: fetchProducts falls back to a direct product fetch, and both purchase surfaces show an error with Try again and keep a free exit.
  • Restore outcomes invisible: Settings, Recharge+ tab, paywall and offer page each show a success or error line from store.lastError.

  • Crash scan: the only force unwraps are constant URLs and the last-resort in-memory ModelContainer try!; Int conversions in view code are on bounded values; no array index without a guard found in the files read.
